## Architecture Overview

This document describes the layered architecture, data flow, and rationale for key patterns in the Pharma Risk Management Backend.

### Layered Flow Diagram

```text
Core Layer
├─ Domain
│  ├─ Common
│  └─ Entities
│     ├─ Pharma RM
│     └─ Shared
└─ Service
   ├─ IRepositories
   ├─ IServices
   ├─ Services
   ├─ Managers
   └─ DependencyInjection

Infrastructure Layer
└─ Persistence
   ├─ Migrations
   ├─ Repositories
   │  └─ Pharma RM
   └─ ApplicationDbContext

Common / Shared Layer
├─ Exceptions
└─ Models
   └─ Dtos
      └─ Pharma RM

Web API Layer
├─ Controllers
│  └─ Pharma RM
├─ Middleware
├─ Configuration
├─ appsettings.json
├─ appsettings.Development.json
└─ Program.cs

Test Layer
└─ Tests
   └─ Pharma RM
```

### Request/Response Flow (high-level)

1) Request enters controller and model validation occurs.
2) Controller calls service via `IService` abstractions.
3) Service orchestrates repositories via `IRepo` interfaces.
4) Repositories use `DbContext`/Dapper to access database.
5) Service maps entities to DTOs and returns result.
6) Middleware converts exceptions to consistent API error responses.

---

## Core Layer

- **Domain**: Defines entities and base models for persistence.

- **Service – Repository Interfaces (IRepo)**: Contracts abstracting data access operations and persistence details.
- **Service – Service Interfaces (IService)**: Business operation contracts independent of infrastructure concerns.
- **Service – Service Managers**: Orchestrate business logic using repositories and mappers.
- **Service – Dependency Injection Setup**: Central service registration and lifetime configuration for DI.

### Domain details

- Entities model database tables with data annotations for validation/mapping.
- Includes shared base types (e.g., `BaseEntity`) for audit fields and IDs.

Example entity using data annotations:

```csharp
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

[Table("Auditors")]
public class Auditor
{
    [Key]
    public Guid Id { get; set; }

    [Required]
    [MaxLength(150)]
    public string FullName { get; set; } = string.Empty;

    [Required]
    [EmailAddress]
    [MaxLength(200)]
    public string Email { get; set; } = string.Empty;

    [MaxLength(30)]
    public string? Phone { get; set; }

    // Foreign key example
    //[ForeignKey(nameof(Department))]
    //public int DepartmentId { get; set; }
}
```

Why data annotations?

- Keep validation and schema hints near models for maintainability.
- Enable EF Core to infer schema and constraints automatically.
- Provide lightweight, discoverable validation for DTO mapping consistency.

### Service details

- `IService` defines use-cases; implementations coordinate repositories, mapping, and validation.
- `IRepo` defines persistence operations; implementations hide EF/Dapper specifics.

Why Service Manager and Repository Manager?

- **Service Manager**: Single composition root for services, enabling cohesive DI and easier testing.
- **Repository Manager**: Aggregates repositories behind one dependency, simplifying service constructors.
- Both support unit-of-work patterns and transactional consistency when needed.
- Reduce coupling to concrete classes and centralize lifetime management.

Typical DI lifetimes:

- `DbContext`: Scoped per request.
- Repositories/Services: Scoped; stateless logic depends on scoped context.

## Infrastructure Layer

- **Persistence – Migrations**: Versioned schema changes managed through Entity Framework migrations.
- **Persistence – Repositories**: Data access implementations using EF Core and Dapper.
- **Persistence – Application DbContext**: EF Core context managing entities and database connections.

Details

- `ApplicationDbContext` tracks entities, relationships, and performs change detection.
- Repositories encapsulate queries, projections, and performance optimizations.
- Dapper is used for targeted, high-performance read/write scenarios.
- Migrations provide deterministic, auditable database evolution across environments.

---

## Common / Shared Layer

- **Exception**: Custom exception classes for consistent error propagation.
- **Models**: DTOs, API responses, and standardized error response objects.

Details

- Common response wrappers standardize payloads and error formatting.
- Exceptions bubble to middleware for unified, predictable error handling.

---

## Web API Layer

- **Controllers**: HTTP endpoints exposing application features and validation.
- **Middleware**: Cross-cutting concerns like exception handling and logging.
- **Program.cs**: Application bootstrap, host configuration, and pipeline composition.

Details

- Controllers validate inputs, call services, and shape responses.
- Middleware handles exceptions, logging, and correlation IDs consistently.
- `Program.cs` composes DI, logging, EF Core, and Swagger configuration.

---

## Test Layer

- **Tests**: Unit and integration tests validating business and API behavior.

Details

- Unit tests mock repositories/services to verify business rules quickly.
- Integration tests exercise API endpoints and persistence behavior.
